SureWord/Product Opportunity Audit/2026-09-12

Fix the first ninety seconds, then make chat a companion that knows the day.

The chat chrome is real and cheap to cut, but it is not the leak. The leak is a new user on the web tapping a canned question, receiving a 2,949-character essay from an assistant that does not know their name, and never coming back. Most of the fix is server-side and reaches all four clients on one deploy.

Prepared by Claude Code · Read-only audit, nothing implemented · 11 area agents, 4 cross-cutting agents, 8 specialist reviewers · Production data from Neon neondb (44 users) · Working tree at 2e6e99b plus uncommitted verse-actions work
Summary Findings Ranking Recommendations Rejected Method

Verdict

Confirmed in production data

SureWord has an activation problem dressed as a chat-density problem. 36 of 44 accounts used the app on exactly one calendar day, with a median lifetime under two minutes. Every account that returned had the reader, a push token, or a daily cross; none of the leavers had any of the three. The chat "feels like too much" for the same reason new users bounce: the server asks for conversation while the client draws a document and the prompt never tells the model who it is talking to.

The highest-leverage work is one server release (know the user's name, know the day, answer short) and one client release (a quiet turn with actions on hover or long-press, and a single receipt line for every write). Both are S effort. The bigger bets (a walk history, an evening close, prayer follow-up) are good, but they serve five accounts today and belong after the first-run fixes.

What the audit found

Eight findings that reorder the work. Each one was verified against the repo or the production database, not inferred from a feature list.

Returning users are the ones who touched the reader or got a morning contact, not the ones who chatted longer

Confirmed

First-conversation length was 2.81 messages for users who never returned and 3.13 for those who did, so chat depth does not predict return. Of the 8 returners, 5 had a push token, 4 read a chapter, 5 received a daily cross. Of the 32 leavers, zero had any of the three. This is n=40 and correlational, but it is the only directional evidence in the data and it points at the day loop, not the chat turn.

Evidence

Read-only SQL over Message, ReadingEvent, PushToken, VerseOfDay in neondb (PM and Growth reviewers, re-run independently). Only 5 of 44 accounts have ever had a push token; 0 of the 28 accounts created March to July installed the native app. Web is 89% of the user base and has no retention channel: User.email is never synced (src/lib/auth.ts:124 has zero callers) and the morning cron iterates push tokens only (src/app/api/cron/verse-of-day/route.ts:90).

The chat is heavy because the client amplifies structure the prompt already asks the model to avoid

Confirmed

The system prompt asks for "one to three short conversational paragraphs with no headings" on follow-ups (src/utils/systemPrompt.ts:29), then ships 28,700 characters of expository framing every turn with no mechanical enforcement. On Android a two-paragraph follow-up carries about 234px of furniture under 180px of prose: an unconditional "Add to notes" row, a collapsed "Retrieved Verses (6)" card with a similarity percentage per verse, a captioned follow-up block, and an avatar on every row. On web the markdown renderer puts a lightbulb on every h2, a checkmark on every bullet and a tinted card on every blockquote.

Evidence and per-element verdicts

mobile/src/features/chat/MessageBubble.tsx:108-148 gates every card on settled, never on the answer's weight. mobile/src/features/chat/MarkdownBody.tsx:40-53 maps a model h1 to the app's 22px screen-title style. src/components/markdownComponents.ts:175-199, 273-292, 339-371 adds the icons. src/components/ChatInput.tsx:312-323 prints an AI disclaimer and a creator byline under every turn. The match badge is false signal: src/lib/bible/verse-fulltext.ts:156 returns rank / topRank, so the exact-word tool's top hit is always 100% and is then averaged with a cosine score at src/components/useChat.ts:309-315.

The assistant knows the app but not the person

Confirmed

On turn one the model receives a full product tour (appKnowledge) but not the user's name, today's cross, their plan day, what they read this week, or what they highlighted. User.name is null for 43 of 44 accounts because the only function that syncs it has zero callers, while the spoken devotional works around this and prays for the user by name. The volatile prompt carries memories and church only (src/app/api/ask-question/route.ts:702), even though loadStudyContext already assembles reading, notes, plan and today's verse for the welcome chips and the daily cross.

The writes Austin cares about are invisible, and the reads the model does for itself are loud

Confirmed

Note saves get an amber card and the daily cross gets a three-line card. Memory saves, memory edits, plan starts and plan ticks leave nothing once the stream ends: useChat.ts:265-284 and mobile/src/lib/chatView.ts:234-253 build receipts for two tools out of eight write tools. All four memory tools have fired zero times in production. The window is only six days, but the older zeros are the telling ones: getHighlights, setDailyCross and both plan writes have never fired either. A tool nobody sees fire is a tool nobody learns exists.

The backend is a release ahead of every client

Confirmed

Reading history has a POST and no GET (231 rows nobody can see). The highlights list function with totals and verse text exists and is reachable only through a tool that has never fired. 21 provenance columns on VerseOfDay (theme, evidence, why-today) are written daily and read by zero clients; the day itself is unreachable after 20 hours. 225,683 cross-reference edges have no UI. Note semantic search is maintained on every write and no search box calls it. The plan's todayDay ships in every payload and no client renders "3 days behind".

27 conversations hold a user question and no assistant answer

Defect, unexplained

Verified today: 27 of 339 conversations across 15 users, 13 of them since August 1, so this is not only the stream-disconnect bug fixed earlier. Twelve belong to one-day users, which is a third of everything that cohort ever started. Nothing measures whether an answer arrives. There is no product instrumentation of any kind: the only telemetry is a shape-only console.info and neither package manifest has an analytics or error-reporting dependency.

WITH c AS (SELECT c.id, c."userId", c."createdAt",
  COUNT(*) FILTER (WHERE m.role='user') u, COUNT(*) FILTER (WHERE m.role='assistant') a

SELECT count(*) FILTER (WHERE u>0 AND a=0)                      -- 27

     , count(*) FILTER (WHERE u>0 AND a=0 AND "createdAt">='2026-08-01') -- 13
FROM c;

The working tree cannot be shipped by committing only the modified files

Release trap

The modified ask-question/route.ts imports @/lib/ai/prompt-cache and @/lib/ai/chat-metrics. Both are untracked, as are answer-eval.ts, the three tests, scripts/eval-answers.mjs and its fixtures. The committed route has zero references to them, so production has no prompt-cache split, no step-limit metric and no eval harness today. A "commit touched files only" push breaks the Vercel build on a missing module. The same tree carries an iOS compile break: macos/SureWord-iOS/Views/Bible/BibleTabView.swift:10 declares let translation: TranslationID? = nil, which Swift omits from the memberwise init that lines 80-85 call with four arguments.

Five more live defects sit under the opportunities

Fix first
  • Push fan-out per token. The morning cron sends one push per token (cron/verse-of-day/route.ts:125); one account with 143 tokens receives 76 identical notifications. src/lib/push.ts:112 also filters chat replies on enabled, contradicting the schema comment at prisma/schema.prisma:384-387.
  • Cold permission prompt. Android requests notification permission seconds after sign-in (mobile/app/(app)/_layout.tsx:112 with enabled: true default) before the user has seen a verse. A denial is effectively permanent on modern Android and it is the product's only retention channel.
  • The welcome screen makes a claim the server computed to be false. "CHOSEN FROM YOUR STUDY" and the hero paragraph render for new accounts while src/lib/suggested-questions.ts:126 returns personalized: false and no client reads it. src/lib/daily-cross.ts:75 already states the honesty rule the welcome copy breaks.
  • Empty notes feed personalization. 61 of 136 notes are empty and 65 are "Untitled Note"; two accounts have - Untitled Note: in their daily-cross context today. One where clause at src/lib/study-context.ts:73.
  • PARITY.md:111 is false. It marks note-receipt cards done on macOS while macos/SureWord/Chat/Views/ChatView.swift:154 still answers taps with "Notes arrive in a later phase."

Where the reviewers disagreed

Eight seats scored independently. Agreement was near-total on the top three; the disputes below are recorded rather than averaged away.

  • Receipts (#9). Five wave-1 reports made it the consensus top pick. The PM, UX and red-team seats pushed back: it renders writes that have fired 15 times ever, and the binding constraint is invocation, not visibility. Kept at #9, shipped with #5 so the reclaimed amber budget is spent on it, and with #8 so there is something to render.
  • My Walk (#16). The surface-stored-data thesis argued one journal beats five screens; the new-user and red-team seats note 35 of 44 accounts would see an empty page. Kept as a strategic bet; its server half (#7) ships first and stands alone.
  • Voice. The companion thesis wanted device text-to-speech and no mic (Gboard already dictates); the red team says device TTS is below the brand's ElevenLabs bar and no speech module is installed either way. Deferred entirely; see Rejected.
  • Android-first vs where users are. CLAUDE.md makes Android the primary client. 89% of accounts are web-only and no account created March to July installed anything. The parity rule is sound engineering discipline; it is not an audience claim, and the ranking above favors server-side work partly for that reason. This is Austin's call, not the audit's.

Method

Read-only. No repo file was modified. Three waves of agents, then this synthesis.

  • Map. Directory tree, docs/FEATURES.md, docs/PARITY.md, docs/PLANNED-FEATURES.md, the 24-tool registry, the system prompt, the Prisma schema.
  • Wave 1, eleven area agents: web chat UI, Android chat UI, chat engine, memory and personalization, notes, Bible reader, Pick Up Your Cross and Listen, reading plans and atlas, settings and growth, data model and backend inventory (with production counts), Apple clients and parity. 87 opportunity blocks with file:line evidence.
  • Wave 2, four cross-cutting agents: a merge editor (87 blocks to 57 candidates, plus verification of three disputed claims and eleven contradictions), and three theses: the conversational companion, surfacing stored data, the daily rhythm and retention.
  • Wave 3, eight reviewers scoring independently: product manager, UX designer, power user, new user, domain expert, software architect, growth, red team. The PM and growth seats ran their own retention SQL; the red team spot-checked 15 citations and found three stretched (conversation route already returns updatedAt; the verses card is collapsed by default on every client, so that part of the density evidence was wrong; a middleware allowlist miscount).
  • Independently verified by the lead: the 27 unanswered conversations (query above), the untracked AI modules and the committed route having zero references to them, the conversations route's updatedAt, and the absence of cross-references from the mobile tree.
  • Production data came from read-only queries against Neon neondb (project versemind), identity confirmed by current_database() and a 44-user count, never the empty decoy. Numbers are a snapshot at 2026-09-12; the memory tools shipped six days earlier, so their zero is partly recency.
  • Not done: no screenshots, no runtime on device or emulator, no light-mode rendering check, no Apple build. Effort estimates are from reading code, corrected where the architect or red team found a hidden migration or parity bill.
  • Working files: all agent reports are in the session scratchpad under wave1/, wave2/, wave3/; the master candidate list is wave2/master-candidates.md.
