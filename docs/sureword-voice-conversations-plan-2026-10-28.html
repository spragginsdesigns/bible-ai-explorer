Start once, then talk back and forth.

Proposed experience

Add a clearly named Talk to SureWord button beside the composer and on the chat home. After permission and a short spoken introduction, the user asks a question, hears the answer, and continues in the same thread without tapping Send each time.

Controls and turn behavior
  • Listening, Working, Speaking, Paused, and Connection lost are both visible and accessible; a waveform or color is never the only signal.
  • Provide Finish speaking, Cancel recording, Stop speaking, Pause listening, Replay answer, and End conversation. No hold gesture or precise touch is required.
  • Detect the end of speech with a configurable pause; start testing around 1.2–2 seconds. Offer a manual mode with one stable accessible Start/Finish control for slow speech, long pauses, or noisy rooms. Read back the recognized request on demand and allow correction or cancellation before execution.
  • Re-arm listening after playback/cues drain and the previous turn is durably saved. If capture starts earlier, hold its transcript until the canonical parent version is available. First release is turn-taking; speaking over the assistant is a separate echo-cancellation and interruption gate.
  • Replay, slower/faster speech, and stop/resume use existing output, without spending another AI answer. Add Read aloud to old answers outside Talk mode.
  • First release uses an explicit foreground session. Backgrounding or locking pauses microphone capture; resume is deliberate. Background calling and wake words are later scope.

Voice and typing share one history and one set of capabilities.

Product contract

Save finalized user speech as ordinary user text, and save SureWord's full answer, citations, and tool results in the same conversation. A person can switch to typing, close the app, or reopen the thread on another device.

What “all its tools” means

Preserve Scripture retrieval, KJV passages, original languages, Atlas, web search preferences, notes, highlights, memories and prayer, Daily Cross, reading plans and journal, Learn, church and sermon context, Serve, and ongoing studies. These remain subject to the same entitlement, ownership, context, and confirmation checks as typed chat.

Render tool cards for sighted users and speak their useful outcome. Read available choices with stable labels and support an answer such as “the second one.” If a tool opens a screen, announce the destination and offer to read its content; opening a visual screen alone does not satisfy a spoken request.

Do not narrate internal reasoning or raw tool JSON. Say that a note was saved only after its server receipt exists. The current registry is src/lib/ai-tools.ts:1669–1704, including its six spread builders.

Saved text and spoken meaning must agree.

Release requirement

Speak the approved answer with plain, warm, unhurried delivery and an adjustable speed. Format references for speech, preserve exact KJV quotations, and keep the existing doctrinal foundation in the shared backend.

Speech rendering and interruptions

Use full-answer narration as an engineering baseline. The first user pilot must stream completed, stable sentences or clauses, or demonstrate that full-answer narration meets the measured response targets. A speech renderer removes Markdown and expands references such as “First Corinthians, chapter thirteen, verse four”; it must not silently rewrite theology, quotations, or action results.

The full answer remains in the log when playback is interrupted. Record playback separately as partial/stopped, and offer “read the rest.” Generated text, synthesized audio, and audio actually played are different facts; never mark the entire answer as heard merely because generation completed.

If GPT-Live paraphrases an approved result, its actual spoken transcript also needs to be stored and tied to that result. Exact Scripture can use a verified rendered clip with Live output controlled while it plays. A prompt alone is not proof that the spoken words matched.

Screen-reader use is part of the core flow.

Release requirement

Test with TalkBack and VoiceOver enabled, with the screen hidden. Keep focus stable, announce state changes without reading every token, and provide one clear route to stop audio or leave the session.

Speech ownership, failure, and privacy
  • Offer natural app narration or device/screen-reader reading for answers, with an explicit preference. Avoid duplicate automatic full-answer announcements; never require disabling the screen reader.
  • Coordinate chat narration, Bible audio, devotional audio, microphone capture, headphones, Bluetooth, and system interruptions in one audio controller per client. Announce readiness only after capture initializes; exclude app cues/status speech from input and suspend automatic capture during app announcements.
  • Prevent self-transcription and measure ambient false activations on hardware. Provide pause/manual capture and transcript correction; ambient speech must never bypass protected-action confirmation.
  • Read permission, network, quota, transcription, and playback failures with an actionable recovery. Keep the transcript when audio fails, and avoid silent fallback failures.
  • Tell users they hear an AI voice and that their transcript is saved with chat. Capture only during an explicit session; save raw microphone audio only with a separate opt-in.
  • Verify screen-reader navigation cannot become user input. Where reliable coordination is unavailable, provide explicit accessible Start/Finish capture with the screen reader enabled.
  • Keep transcripts and synthesized personal audio private and account-scoped. Use short-lived playback URLs, a defined audio cache lifetime, deletion with the conversation/account, and no transcript text in analytics. Vendor retention terms require separate review.

The status behavior follows W3C guidance on accessible status messages. This plan is not a claim of accessibility conformance.

The five backend contracts that must precede automatic retries
  1. One canonical spoken turn. Require/create an owned conversation before accepting input. Commit finalized mic speech into user text; keep arbitrary uploaded recordings as quoted attachment content.
  2. One server-owned turn identity. Use a stable turnId, conversation parent/version, and canonical user/assistant IDs. Load validated history from the server; serialize committed turns in a thread and reject or reconcile stale parents.
  3. Idempotent writes and durable save events. Uniquely claim each turn, tool operation, and synthesis segment; replay stored results on retry and charge once per segment. Save user text before work; return turn.saved only after assistant text/tool results are durable. Reconnect by ID, without generating again.
  4. Separate stopping audio from cancelling work. Stop speaking clears playback immediately. Cancel pending work blocks unstarted writes and suppresses obsolete output, while completed actions keep their receipts. End conversation closes capture and transport according to an explicit drain/cancel policy.
  5. Exact spoken approval. Bind a final explicit “yes” to the active proposal, exact arguments, and a later user turn. Keep the existing fingerprint/expiry/ownership rules; ensure the proposal was presented accessibly before using a bare confirmation.

Proposed runner input: userId, conversationId, turnId, parentVersion, canonicalText, inputMode, locale, timezone. Proposed output events: user saved, progress, tool receipt, answer text, speech segment ready, turn saved, terminal state. These are design contracts, not existing APIs.

Suggested storage: a durable turn record with unique IDs and state; per-operation receipts for mutating tools; message metadata linking input mode and logical voice session; separate speech segment/playback records. Apply schema migrations only during implementation. Keep transport records subordinate to the existing conversation and account deletion paths.

Why GPT-Live is a prototype, and why legacy OpenAI TTS is not the baseline

OpenAI's architecture guide now supports a full-duplex voice frontend with an independent existing backend. Client delegation is the fitting mode for SureWord; it retains our context and tool execution rather than rebuilding them in a hosted configuration.

Two documented constraints matter here: Live commentary may paraphrase supplied results, and transcript fragments have timestamps but no completed-turn event or item ID. We must group turns, record actual speech, preserve exact quotations, and handle corrections while work continues. Sources: Client delegation and Live transcript behavior.

For a secure Live architecture, plan a persistent server-side session controller and sideband control connection, keeping authorization and credentials server-owned. Verify native WebRTC support in the actual Expo and Apple builds, project access, session lifecycle, regional/network behavior, and operating cost before choosing a call service. Do not assume an ordinary five-minute Next.js route can own an arbitrarily long voice call; Vercel documents bounded function duration.

OpenAI's TTS guide currently marks tts-1, tts-1-hd, and gpt-4o-mini-tts for shutdown on January 6, 2027. It says the replacement uses the Realtime API rather than /audio/speech; avoid starting a new long-lived integration on those legacy models.

Performance targets and proof package

Proposed pilot targets, not measured results: median first useful audible answer within 3 seconds of the user’s last spoken word and p95 within 7 seconds for ordinary no-tool questions; Stop speaking silences playback within 300 ms. Include endpoint detection in that user-facing total; also measure committed-turn latency, transcription, backend first useful text, speech first byte, and actual audible playback separately.

Tool-heavy requests get truthful accessible progress, with the full task time reported separately. A filler acknowledgment does not count as the answer. Use deterministic replay tests for duplicate delivery and interruption, then representative human recordings and live sessions.

Record device/build, network, configuration, timing, screen-reader settings, server turn IDs, saved history, and tool receipt checks. A successful simulator run does not establish microphone routing, Bluetooth, or blind usability on physical hardware. Pilot with a blind participant; Austin's mom is the motivating user, and participation remains her choice.

Build in five bounded work packages.

Owners below are engineering roles, not assignments already sent to a team. No implementation, deployment, or external issue creation is part of this planning task.

  1. Audio prototype, Android owner. Capture actual microphone speech, submit one finalized turn through the shared engine, and compare Flash/device narration. Measure first audible answer, long pauses, exact quotations, and screen-reader behavior. Prototype GPT-Live client delegation separately to resolve the full-duplex tradeoff.
  2. Durable turn contracts, backend owner. Extract the shared runner without changing doctrine. Add canonical history, turn/operation identity, durable-save acknowledgment, stale-result handling, and playback-versus-work cancellation. Prove reconnect, approval, quota, and deletion behavior before automatic retries.
  3. Accessible conversation, Android + backend owners. Build the hands-free turn-taking loop, transcript, replay/rate controls, tool outcome narration, permission/recovery flow, and audio coordinator. Gate rollout by account/server flags and exercise the real Android path first.
  4. Capability parity, web + Apple owners. Implement the same contract with native layouts on web, iOS and macOS. Rebuild capture permissions, test real audio hardware, and update docs/PARITY.md; no untested platform is marked complete.
  5. Blind-user pilot and release, accessibility + release owners. Review recorded evidence and actual saved/tool state, choose allowances and voice defaults from measured cost, then ship through the normal Android/web/Apple gates. Keep full duplex gated until it meets the same fidelity and interruption tests.
