Build a hybrid progress system

Proposed

Keep tool updates deterministic, add concise public model summaries, and make long waits actionable. SureWord already streams status data, but its current model and rendering choices leave long gaps with little to say. Start with the existing stream; evaluate a separate narrator only if the resulting language still needs work.

The current code leaves gaps in narration

These behaviors are verified in local source. The screenshot alone does not reveal its model, elapsed wait, or network condition.

Status changes depend almost entirely on tool events

Confirmed

The route emits “Getting ready,” then “Thinking,” then a tool label while a tool executes. Every tool completion resets the line to “Thinking,” and the writer has no mechanism to describe a long interval inside the model.

Source evidence

src/app/api/ask-question/route.ts:716, :838, :898; src/lib/ai/status-narration.ts:35.

onToolExecutionStart: ({ toolCall }) => {
  writeStatus(toolActivityLabel(toolCall.toolName));
},
onToolExecutionEnd: () => {
  writeStatus("Thinking");
}

The writer reuses id: "status", which is a good basis for an updating row. Labels use tool names but not passage references or completed results. The client can override server copy with its own generic label during pending tool parts.

OpenAI summaries are off, and mobile ignores reasoning parts

Confirmed

buildProviderOptions explicitly sets reasoningSummary = null. Mobile converts text, status and tool parts to visible content, skipping reasoning parts, so turning summaries on by itself would not make them visible.

Source evidence and provider limits

src/lib/ai/models.ts:772; mobile/src/lib/chatView.ts:208. Installed @ai-sdk/openai defaults summaries to detailed when reasoning effort is present, and explicit null overrides that default.

The local house model is GPT-5.6 Luna at medium effort; the BYOK route can default opening questions to high when no preference overrides it. This does not identify the screenshot's configuration.

The code comment attributes the summary setting to cost. That is a rationale, not a measured billing result: OpenAI's 2025 announcement described summaries as available at no additional cost. Verify current model usage and latency instead of assuming the comment proves a saving.

Any answer text hides server status

Confirmed

The mobile mapper hides server status once text exists, while allowing active tool labels to remain. A brief opening acknowledgment would therefore suppress later server narration unless progress and answer content are modeled separately.

Code and existing test

mobile/src/lib/chatView.ts:276; matching behavior exists in src/components/useChat.ts:305.

const activity = toolActivity ??
  (content.trim() ? undefined : statusActivity);

npm test -- src/lib/chatView.test.ts passed 34 tests. The existing test at line 326 explicitly asserts that status disappears after text arrives. This is current behavior, not proof of a repaired experience.

Long waits need a clearer recovery and stop contract

Code gap

The server allows 300 seconds, but mobile recovery gives up after 150 seconds. The “Stop generating” control visually shows another spinner, and the server is intentionally designed to finish after the client disconnects.

Source evidence and implication

src/app/api/ask-question/route.ts:75 sets maxDuration = 300; mobile/src/features/chat/useSureWordChat.ts:101 sets RECOVERY_MAX_MS = 150_000 and still describes a 120-second route.

src/lib/ai/tool-loop-budget.ts:11 sets a 210-second loop budget. It is checked between steps, so it is not a hard interrupt for a stalled individual call.

mobile/src/features/chat/ChatInputBar.ts:285 labels a spinner “Stop generating.” useSureWordChat.ts:391 stops client streaming, while the server drains the response at route.ts:906 and :928. A real server cancellation signal must be distinct from leaving the app.

The mismatch could make a late answer appear failed after a disconnect. I have not reproduced that condition on a device.

If a narrator is added, feed only approved public summaries and sanitized event facts, cap it to one short sentence, deduplicate inputs, allow one in-flight call, and drop outputs whose run or sequence is stale. It must never delay the answer or require a new provider for a BYOK user without an explicit product decision.

A calm row that gives the wait meaning

One headline, one short explanation, optional elapsed time, and expandable activity. This interactive example uses fictional events and timing, not a replay or measured performance.

Example question: Why did Jesus turn water into wine in John 2? I thought we weren't supposed to drink alcohol.

Your question is ready to send.

Activity for this simulated turn

    Keep the narrative useful

    “Opening John 2:1–11” should come from the actual passage request. “Considering how this relates to drunkenness” should come from a public model update, not a timer guessing what the model might do.

    Prefer a complete short sentence every meaningful transition. Start with a 4–6 second cadence for narrative replacement, coalesce bursts, and show errors or cancellation immediately.

    Handle silence honestly

    When there is no new information, keep the last activity and show elapsed time. Around 30 seconds, add a neutral waiting notice and a clearly visible Stop control; offer background completion only when supported for that run.

    Distinguish “Still waiting for the response” from “Connection lost.” A live server heartbeat proves connectivity, not model progress.

    Rendering and event rules

    Priority: failure / connection / cancellation state, then currently running tools, then the latest provider progress update, then a neutral wait fallback. Keep pending parallel tools as a set keyed by call ID; one tool ending must not reset another to “Thinking.”

    Content: maintain separate progress, commentary and answer fields. Never hide all progress because a preamble exists; collapse it when substantive answer text streams and bring it back if tools resume.

    Lifecycle: attach run ID, increasing sequence, event time, phase, source and optional tool-call ID to progress. Keep a current snapshot plus a small completed-activity list; terminal state wins over late summary callbacks.

    {
  type: "data-progress", id: "progress",
  data: {
    runId: "...", sequence: 4,
    phase: "tool", source: "tool",
    toolCallId: "...",
    headline: "Opening John 2:1–11",
    detail: "Looking at the wedding passage you mentioned."
  }
}

    Storage: keep transient progress out of answer text, conversational memory and embeddings. Preserve provider protocol blocks unchanged where required; store durable run state separately for recovery. If choosing SDK transient: true, wire onData on every client first, since the current mapper reads message parts.

    Accessibility: normal readable type instead of tiny italic copy, restrained motion, no forced scrolling, polite announcements on meaningful changes, and no screen-reader announcement for every elapsed second. Use an obvious square Stop icon or text label.

    Build and evaluate it in this order

    1. Instrument the actual wait. Add client timing for acknowledgment, first meaningful status, first answer text and longest progress gap. Separate setup, provider, tool and network delay.
    2. Prototype the shared progress contract on Android. Reuse SSE, add passage-aware tool labels, distinct quiet/reconnecting states and a visible Stop action. Align recovery deadlines with server run state.
    3. Run a provider-summary experiment. Enable summaries only on supported chat models and render them separately. Compare event-only progress against event-plus-summary using real questions before deciding on a narrator.
    4. Reduce delay and prove the full path. Inspect redundant tool calls, cache behavior and effort settings against answer quality. Validate Android first, then web and Swift clients; commit or release only after the design decision.
    Proposed acceptance checks and measurement

    Scenario set: the supplied John 2 question, an ordinary no-tool question, a factual passage lookup, a personal follow-up, a document, original-language research, multiple concurrent tools, a failed lookup, a quiet provider, and app background / foreground with a slow answer. Include the house model and representative supported BYOK providers.

    Experience checks: immediate send acknowledgment; no static unexplained wait beyond the long-wait threshold; real references and results in tool updates; no stale updates after answer completion; preserved answer after reconnect; explicit failed and cancelled states. Prompt-only preambles and tool labels must not be counted as first answer text.

    Metrics: p50/p95 time to first useful feedback and first answer, longest meaningful-progress gap, completion latency, abandonment and retry rates, answer quality, narrator / summary overhead and usage. Existing src/lib/ai/chat-metrics.ts has per-step first-output timing, but that is not the user's time to visible answer.

    Decision rule: choose the simplest variant users can understand throughout the wait, with no material answer-quality loss. If summaries arrive only at the end, do not claim they solve the early gap; improve routing or expose tool stages instead. Do not lower reasoning globally based on one screenshot.
